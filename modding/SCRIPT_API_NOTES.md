# Saints Row (2006) modding notes

Findings from building the Saintify mod. All addresses are guest (Xbox 360)
addresses for the retail XEX this port targets. See also
`modding/mods/ScriptApiDump/` which resolves the full script API at runtime
into `dist/mods/scriptapi_map.txt`.

## Script API mapping (name -> thunk)

- The game registers its ~380 Lua script functions from
  `sub_824E1AD0` (in `saintsrow_recomp.87.cpp`). It builds a stack array of
  `{image string ptr, thunk}` pairs at stride 8 (compiler-reordered; sort by
  stack slot offset to recover the order).
- `modding/mods/ScriptApiDump/scriptapi_pairs.h` is the extracted pair list
  (generated by a python script run over the recompiled source; regenerate it
  the same way if the XEX changes).
- At runtime the game builds a sorted `{thunk, cookie}` table (stride 8) at a
  heap address (seen at 0x92099E60) plus an alphabetical packed string block
  nearby (0x9207xxxx). Cookie = 0x40000000 | (id16 << 8) | flags8; the exact
  id16 meaning is undecoded (not a CRC32/Jenkins/FNV of the name).
- Lua state pointer: `*(uint32_t*)0x82C9AC0C` (loaded by every thunk).
- Thunks take the Lua state in r3 and pull args off the Lua stack via
  `sub_824EFD70(L, -1/-2/...)`; then they resolve script object args
  (handle or name) with `sub_824C5F20` / `sub_824C6498` / `sub_824C6428`.

## Object / character struct layout (partial)

Objects live in the handle table at `0x830866C8`: `object = read_u32(table +
12 + (handle & 0xFFFF) * 16)`, valid iff `read_u32(object+68) == handle`.

| Offset | Field |
|---|---|
| +20 | position (vec3f, all objects) |
| +68 | handle (full, incl. generation) |
| +72 | object type (1 = **any human, incl. the player**; 2/3 = props/corpses, health 0; 5 = vehicle) |
| +212 | dirty flag (player) |
| +216 | flags (bit 0x00100000 = invulnerable, player) |
| +232 | **team id** (write a team id here = set_team; the set_team thunk does exactly `obj+232 = team_id` when team != -1; team name table at 0x820387D8, indexed by team id) |
| +236 | damage-event counter (increments per hit; see sub_82483828) |
| +568 | AI persona sub-object pointer (cower/flee mode at persona+3704, see below) |
| +3552 | **archetype pointer** (character.xtbl entry in memory; the archetype's name is at its +0, e.g. "BF_MID" = black female middle-aged civilian, "HM_3SS3" = hispanic male 3rd Street Saint; personalities like "gang normal" come from here) |
| +3692 | combat flags byte (bit 0x08 = combat disabled; combat_enable clears it, combat_disable sets it - note: does NOT stop civilians fleeing) |
| +1912 | health (f32) |
| +2320 | cash in cents (player) |
| +2496 | current vehicle handle (player) |
| +2569 | transition flags (player; bit 0x10 = entering/exiting vehicle) |
| +3848 | respect (player) |
| +3860 | respect bars (player) |
| +508 | player state (9/12 = in vehicle) |
| +3456 | player: nonzero = not on foot |

Teams (`teams.xtbl` in misc.vpp_xbox2): Playas (= the Saints), Vice Lords,
Los Carnales, Rollerz, Kings, Police, Civilian, Neutral Gang. The team id is
the runtime index; read it from the player object (`player+232`) rather than
hardcoding.

## AI behavior: personality, cower/flee, combat

- NPC behavior at spawn is set per human via script fields (seen in mission
  `.cts` data): `+Team`, `+Personality` ("gang normal", "civilian cowardly",
  "police swat"), `+Cower/Flee` ("never cower or flee", "always cower when
  attacked").
- The **cower/flee mode** is writable at runtime: `set_cower_flee_mode`
  (0x824DA5D0) maps a mode name (5-entry string table at 0x821F9588) to 0-4
  and stores it on the AI persona sub-object at **persona+3704**
  (persona = `entity+568`). **Mode 4 = "never cower or flee"** (calibrated in
  game: converted civilians with mode 4 stopped fleeing and fought back).
  0 = use the personality default (what all ambient NPCs have).
- The **archetype** (`entity+3552`) is the parsed character.xtbl entry,
  SHARED by all NPCs of that type - do not edit it per-NPC. Its name is at
  archetype+0 (8 bytes): "BF_MID", "BM_YNG", "HM_3SS3" (3rd Street Saints).
- `combat_enable`/`combat_disable` only toggle bit 0x08 at entity+3692;
  insufficient to stop personality-driven fleeing.

## WML quick reference

- Native mods: any `*.dll` in the mod folder exporting
  `extern "C" WML_EXPORT int wml_mod_init(const WmlApi*, const WmlMod*)`.
  Build with VS's clang++: `-std=c++23 -O2 -shared -I modding/include main.cpp
  -o dist/mods/<Name>/<Name>.dll -luser32` (see the trainer's Build.ps1).
- `wml.h`: read/write guest memory, `guest_pointer`, `hook` (MinHook on any
  guest function address, chainable, from init only), `call` (inside hooks),
  `on_frame` (render thread), `on_game_frame` (pre-simulation), keyboard
  state, `overlay_text`.
- Enable/disable: `dist/mods/modlist.ini` (`+ Name` / `- Name`).
- Log: `dist/mods/wml.log` via `api->log`.

## Gotchas learned the hard way

- The thunk table/strings the VM uses are built at runtime - there is no
  static binding table in the image; memory scans at mod-init time find
  nothing. The offline extraction route (recompiled source) is the reliable
  one.
- Mod code runs inside the game's process; long scans in `wml_mod_init`
  block startup (looks like a black screen). Defer heavy work to a frame
  callback.
